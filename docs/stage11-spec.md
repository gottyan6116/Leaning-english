# 第11段階：「定義→英単語」形式の追加と、単語帳の各ジャンル④〜⑥の追加

## 目的
1. 既存の「英→英」（単語を見て定義を選ぶ）の逆として、「定義を見て英単語を選ぶ」形式を追加する
2. 各ジャンルのセットを①〜③から①〜⑥に増やす（15セット・150語の追加）
スクリーンショットの提出は不要。変更点、テスト結果、チェックリストの評価だけを報告すること。

## 1. 新しい出題形式「定義→英」
- カード：英英定義を大きく表示する。その下に、例文の見出し語の部分を空欄（___）にしたものを小さく表示する
- 選択肢：英単語4つ。誤答は既存の日→英と同じ条件（同じレベル帯・同じ品詞の別の語。distractorHeadwords を再利用してよい）
- 解説シート：正解の語、品詞、日本語訳、例文（空欄を埋めた完全な文）
- 出題の設定画面の「出題形式」に4つ目として追加する。表示名は「定義→英」
- 成績・苦手・未学習は、他の形式と同じく形式ごとに記録する
- mode の値は、既存の命名に合わせた案を仕様確認時に提示すること

## 2. 自動検証の追加
- 定義の中に、見出し語、その活用形、同じ語源の派生語（例：applicant に対する apply、application）が含まれていないこと。含まれる場合はエラーとする
- 空欄にした例文で、見出し語が正しく1か所だけ空欄になっていること
- 4つの選択肢のどれを空欄に入れても文法的に成り立ちうる場合でも、意味の上で正解が1つに決まること。これは機械では判定できないので、一覧ファイルで目視確認の対象として印を付ける

## 3. データベース
- answer_logs、unit_sessions、preferences の mode の制約に、新しい値を追加するマイグレーションのSQLを作る。既存の値（ja、en、ja_en）と既存の行は変更しない
- 適用済みのマイグレーションの中身は変更しない

## 4. 各ジャンル④〜⑥の追加（15セット・150語）
- 対象：基礎単語、日常単語、ビジネス単語、アドバンス単語、超アドバンス単語の各④〜⑥
- 語の選定元、レベル帯、絞り込みの方法、データ形式、4択の方針は、第10段階（docs/stage10-spec.md）とまったく同じにする
- 同じジャンルの①〜⑥の間でも、ジャンルをまたいでも、見出し語を重複させない
- 1セットの中で、品詞の偏りを避ける（名詞・動詞・形容詞・副詞をバランスよく）
- 全語に、英→日、日→英、英→英、定義→英の4形式の問題を用意する
- 既存の①〜③の150語にも、定義→英の問題を追加する
- 状態はすべて unverified とする

## 5. 画面の細部
- ジャンルの画面のパンくずを「単語帳 ›」から「‹ 単語帳」に直す（戻る操作であるため）
- セットの各行で、丸数字のアイコンと名前の両方に番号が出ている（「① 基礎単語①」）。行のタイトルは「基礎単語」だけにし、番号は丸数字のアイコンで示す

## 6. 守ること
- design-rules.md、design-tokens.css、CLAUDE.md のルールに従う
- 既存の端末内データ、同期、記事、コロケーション、既存の3形式の動作を壊さない
- スコープ外：AI添削、学習時間の計測、記録画面

## 進め方（「止まる」とある工程では必ず止まること）
1. 新しい形式の mode の値、カードと解説シートの構成、自動検証の方法、マイグレーションのSQL案を出力して止まる
2. 承認後、マイグレーションのSQLファイルを作成して止まる。SQLの全文をチャットに出力すること（ユーザーが適用する）
3. 適用の報告を受けたら、定義→英の形式を実装し、既存150語に問題を追加する
4. 各ジャンル④〜⑥の150語を作成し、自動検証を通す。全300語のうち、今回追加・変更した内容を1つの一覧ファイル（ジャンル、セット、語、品詞、訳、定義、空欄の例文、4形式の選択肢、目視確認の印）にまとめ、パスを報告して止まる（ユーザーの内容確認のため）
5. 承認後、コミットして push し、公開版への反映を確認する。テスト結果とチェックリストの評価を報告する
